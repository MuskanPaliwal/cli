## Summary

  PR #2253 establishes one central rule:

  > Checkpoint IDs found anywhere in a commit message may be used for historical discovery, but only IDs in Git’s final trailer block may authorize checkpoint creation, reuse, reconciliation, or
  > mutation.

  Previously, a body paragraph containing Entire-Checkpoint: <existing-id> could redirect operations toward an unrelated checkpoint. That affected PostCommit condensation, attach, generated
  explanations, and legacy session reconciliation.

  There are no new CLI commands, flags, or storage formats. This is a parsing and authorization-boundary change.

  A concrete example:

  Implement feature

  Entire-Checkpoint: A

  Additional body text

  Signed-off-by: Developer <dev@example.com>

  - Read-only historical discovery still finds A, preserving squash-merge history.
  - Mutation paths do not accept A, because the final trailer block contains only Signed-off-by.

  If the message instead ends with:

  Signed-off-by: Developer <dev@example.com>
  Entire-Checkpoint: B

  then B is the mutation-authorizing checkpoint.

  ## Why the parser was split instead of globally tightened

  The checkpoint transcripts record that making ParseCheckpoint globally strict was deliberately rejected.

  Squash merges commonly embed original commit messages like this:

  Squashed commit:

  First change

  Entire-Checkpoint: A

  Second change

  Entire-Checkpoint: B

  Those checkpoint lines are body paragraphs in the resulting squash commit. Resume and read-only history discovery need to find both.

  Unfortunately, a legitimate embedded squash trailer and malicious checkpoint-shaped body text can be byte-for-byte identical. Looking up whether the checkpoint exists does not authenticate it—an
  attacker can name an existing ID.

  Therefore the implementation uses two levels of evidence:

  - Whole-message occurrence: sufficient for discovery.
  - Final-trailer-block placement: sufficient for local mutation decisions.

  “Final-block authority” is intentionally not described as cryptographic trust; a user can still deliberately author a final trailer.

  ## File-by-file explanation

  ### Production changes

  1. cmd/entire/cli/trailers/trailers.go:152

  Introduces:

  - ParseCheckpointFromFinalTrailerBlock
  - ParseAllCheckpointsFromFinalTrailerBlock

  The existing ParseCheckpoint and ParseAllCheckpoints remain permissive, but their contracts now explicitly describe their results as discovery candidates rather than mutation authority.

  The strict parser:

  - Inspects only the last non-empty paragraph.
  - Requires unindented Key: value lines.
  - Allows whitespace-leading continuation lines only after a genuine trailer.
  - Never interprets a continuation as a new checkpoint.
  - Validates checkpoint IDs.
  - Deduplicates multiple IDs while preserving order.
  - Returns the first ID from the singular API.

  finalTrailerBlock was also corrected not to TrimSpace before classifying a line. Otherwise:

    Entire-Checkpoint: A

  would incorrectly become a valid trailer even though Git treats it as body/continuation text.

  HasOPFApplied now follows the same unindented semantics, preventing an indented Entire-OPF-Applied: true from being accepted.

  2. cmd/entire/cli/strategy/manual_commit_hooks.go:145

  All commit lifecycle mutation decisions move to final-block parsing:

  - PrepareCommitMsg no longer lets a body ID suppress creation of the session’s real checkpoint trailer.
  - handleAmendCommitMsg preserves only a genuine final trailer; otherwise it may restore the session’s recorded ID.
  - The agent-commit fast path applies the same rule.
  - CommitMsg checks only the effective final trailer before deciding whether an otherwise empty commit should have Entire’s trailer removed.
  - PostCommit condenses session data only when HEAD has a final-block checkpoint.

  The file also gains source-aware commit-message cleanup:

  - Editor/template flows remove lines Git will treat as comments before locating the final trailer block.
  - -m and -F flows preserve comment-prefixed lines because they are user-supplied content, not editor boilerplate.

  That distinction prevents this -m message from being misread:

  Subject

  Entire-Checkpoint: A
  # actual user content

  Stripping # actual user content would falsely promote A into the final block.

  Comment handling now reads Git configuration in this precedence order:

  1. core.commentString
  2. core.commentChar
  3. Default #

  For auto, it chooses the first candidate not already starting a message line. Entire’s explanatory comments are emitted using that same prefix.

  CommitMsg strips comments for validation only when Entire’s own “Remove the Entire-Checkpoint…” marker is present. That avoids treating arbitrary user-authored comment-looking lines as disposable.

  3. cmd/entire/cli/attach.go:651

  Two decisions are hardened:

  - resolveCheckpointID reuses only IDs from HEAD’s final trailer block.
  - promptAmendCommit considers a checkpoint already attached only if that exact ID is in the final block.

  Consequently, a body reference cannot make attach append a transcript to an unrelated existing checkpoint or avoid adding the real trailer.

  When several final checkpoint trailers exist, attach preserves the previous policy of selecting the last one.

  4. cmd/entire/cli/explain.go:3012

  Adds parseCheckpointForExplainCommit, which chooses parsing policy according to the operation:

  - Read-only explanation uses whole-message discovery.
  - --generate uses final-block parsing because it eventually calls store.Write.

  This is applied to both:

  - Explicit checkpoint explain --commit <ref>
  - Positional target resolution that falls back from checkpoint lookup to a commit

  This preserves squash-history explanation while stopping generated summaries from being written to a checkpoint named only in commit-body text.

  5. cmd/entire/cli/strategy/manual_commit_migration.go:33

  Legacy states may lack LastCheckpointCommitHash. Previously, a whole-message match against LastCheckpointID could select the reconciliation path and realign both BaseCommit and
  AttributionBaseCommit.

  Now the ID must appear in the final trailer block. A body-only match falls through to ordinary migration, leaving the attribution base pinned.

  The recorded rationale is that backward compatibility should not allow weaker evidence to mutate future attribution.
