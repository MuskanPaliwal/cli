Current proposed minimal patch

- In the interactive path, a detail/body seed read failure returns `could not load current trail body: %w` before opening the form or writing anything.
- In the non-interactive path, when a body update is requested without explicit overwrite, the detail/ETag verification happens before any metadata PATCH. A read failure returns `could not verify trail body is unchanged: %w`; it no longer warns and falls back to overwrite.
- `sendTrailBody` now sends `overwrite: true` only for explicit overwrite. With a nonempty ETag it sends `If-Match`. With no ETag and no explicit overwrite it sends neither, relying on the server's guarded semantics: an absent/empty body document can be created or cleared, while an existing nonempty body should conflict rather than be overwritten.
- The internal helper's now-unused error-writer parameter was removed and its test call sites updated.
- Tests were updated so missing ETag without explicit overwrite expects a guarded body request, explicit overwrite remains the negative control that skips the verification GET and sends overwrite authority, and the 409 conflict mapping remains covered.

Do not accept this design merely because it is already implemented. Independently verify the old-server/no-body-document contract. In particular, determine whether a successful detail response without an ETag is a legitimate absent-body case, whether sending neither `If-Match` nor overwrite is supported by old and current servers, and whether any server version interprets that request unsafely. If that assumption is not supported, stop and report the compatibility risk rather than widening the patch speculatively.

Also review:

- explicit `--overwrite` semantics and its guarantee that no verification GET is required;
- both non-interactive and interactive paths;
- partial metadata/body updates and the ordering that prevents metadata mutation before a failed body verification read;
- clearing an absent body document;
- 409 conflict behavior;
- whether any request can still mutate after a verification or seed read fails;
- whether the error messages follow repository conventions;
- whether removal of the internal error-writer parameter has unintended callers.
