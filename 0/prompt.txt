- In `runTrailUpdateWithClientAtPath`, a non-interactive body update tries to fetch the current body/ETag. If that GET fails, the command only warns and continues with an empty ETag.
- In `sendTrailBody`, an empty ETag is treated the same as explicit overwrite authority: the request is sent with `overwrite: true` and no `If-Match` header.
- The interactive path can reach the same failure direction after a body seed read fails.
- The current test `TestRunTrailUpdateWithClient_EtagFetchFailureWarnsAndFallsBackToOverwrite` simulates a 500 detail response, then asserts command success, `overwrite: true`, an empty `If-Match`, and a warning. On canonical main, the focused test passes, proving the unsafe behavior is deterministic and intentionally codified.
- Git history shows this compatibility policy was deliberate: `d3f920f01270` added `If-Match` while preserving missing-ETag overwrite fallback; `0dc4af34ddb` added the warning while keeping that fallback. Checkpoint transcripts for those commits were not available locally, so call this commit-backed intent, not transcript-backed intent.
- The behavior originated in merged entireio/cli PR #2079 (`https://github.com/entireio/cli/pull/2079`). No later commit in the refreshed refs removes it. Indexed public searches found no separate issue or fix, but the negative search was not exhaustive because live GitHub API search was network-blocked and Entire semantic search required login.
- The safety invariant is: inability to establish the current body version is not authority to replace it. Default updates should fail closed. Only an explicit `--overwrite` should authorize an unconditional replacement.
