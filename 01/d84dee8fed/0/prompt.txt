We investigated entireio/cli#1065: Claude Code can hang at startup because its SessionStart hook launches:

  entire hooks claude-code session-start

  The issue report says the real failure is broader than Claude hooks: even entire --version hangs. Samples showed the process
  stuck in _dyld_start, meaning the binary never reaches Go main(). The reported root cause is macOS syspolicyd being wedged,
  not hook stdin parsing or CLI logic.

  Reporter environment from the issue:

  - macOS 26.3.1 (25D2128), arm64
  - Entire 0.5.6 (c9fedb4b)
  - Installed via brew install --cask entire
  - Affected binary: /opt/homebrew/Caskroom/entire/0.5.6/entire
  - Fix reported by author: sudo kill <syspolicyd-pid>

  Local verification environment:

  - Machine: Muskan’s MacBook Air
  - OS: Darwin 25.4.0, arm64
  - Current installed binary: /opt/homebrew/bin/entire
  - Installed target: /opt/homebrew/Caskroom/entire@nightly/0.6.2-nightly.202605150717.11da3db0/entire

  We tested a launch matrix without changing the installed binary:

  1. Current installed nightly: 0.6.2-nightly.202605150717.11da3db0
  2. Latest stable release artifact: v0.6.1 (774ee21f)
  3. Latest nightly release artifact: v0.6.2-nightly.202605160654.ddf1a331
  4. Source build from upstream/main: ddf1a331c4f8e0732ce802d8f56e606a6478ae25

  For each binary we ran, with 5s deadlines:

  <binary> --version

  and the production Claude SessionStart wrapper shape with Claude-style stdin:

  {"session_id":"...","transcript_path":"","model":"claude-sonnet-4"}

  All four binaries passed both probes. The Claude wrapper produced the normal JSON response:

  {"systemMessage":"\n\nEntire CLI will link this conversation to your next commit."}

  The released binaries had com.apple.provenance xattrs; the installed nightly also had com.apple.quarantine. Those xattrs
  alone did not reproduce the bug. spctl -a -vvv -t install returned internal error in Code Signing subsystem on this machine
  for all tested binaries, but codesign -dv showed release binaries signed with TeamIdentifier JN5KA88ZK5, and all launched
  successfully.

  Conclusion:

  - We could not reproduce the hang locally.
  - The failure likely requires a specific wedged macOS syspolicyd state.
  - Because the reported hang happens in _dyld_start, entire hooks ... cannot enforce an internal Go timeout; the binary has
    not started yet.
  - Any mitigation for Claude startup must be outside the child entire process, at the installed hook wrapper / launcher
    boundary.

  Potential plan:

  1. Comment on the issue with the verification matrix and explain that the hang was not reproducible locally.
  2. Propose mitigation:
      - Add external timeout protection to the production Claude SessionStart hook wrapper.
      - If launching entire hooks claude-code session-start does not finish within ~5s, kill it, emit a Claude-compatible JSON
        systemMessage, and exit 0 so Claude Code startup is not blocked.
  3. Add entire doctor launch-health detection:
      - Probe a child entire --version with a short timeout.
      - On timeout, especially on macOS, report likely syspolicyd / Gatekeeper launch-check issue and recovery guidance.
  4. Update troubleshooting docs:
      - xattr -d com.apple.provenance is not reliable on current macOS/SIP.
      - Include diagnostic signature and recovery: sudo kill <syspolicyd-pid>.

  No code changes are currently in the worktree.
